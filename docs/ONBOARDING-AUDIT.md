# 零基础用户上手体验审计与改造方案

> 审计对象：GGUF Benchmark v1.0.1
> 审计方法：实际通读 `start.bat` / `web/index.html` / `web/app.js` / `README.md` / `config/default_config.json`，
> 按「一个从没写过代码、只会在 Windows 上装软件的人」的视角逐步走查。
> 标注 **[已确认]** 的问题均有代码/文档为证，非主观感受。

---

## 一、结论速览

当前流程对**懂一点技术的人**是可用的（有文档、有中文报错、有演示报告）。
但对**零基础用户**有 **4 个「硬卡点」**（自己无法解决，直接放弃）和 **7 个「软卡点」**（能过但很痛苦）。

| 等级 | 含义 | 数量 |
|---|---|---|
| 🔴 硬卡点 | 用户几乎必然卡死，且靠自己无法解决 | **4** |
| 🟡 软卡点 | 能通过，但需要猜、试错或承担误解风险 | **7** |
| 🟢 可接受 | 无需改动 | — |

**四个硬卡点**：拿到程序、准备 llama.cpp、准备 .gguf 模型、耗时完全不可预期。

---

## 二、逐步走查：当前真实流程与卡点

### 阶段 0 · 拿到程序

**当前做法**：README 的「安装」段落直接给出 `python -m venv .venv` 等命令。

**[已确认] 问题 1 🔴 硬卡点 —— 零基础用户不知道怎么"拿到"这个程序**
- 仓库只提供源码。用户要么 `git clone`（不会用 git），要么在 GitHub 页面找 `Code → Download ZIP`（很多人找不到那个绿色按钮）。
- 下载下来的 ZIP 里嵌套一层目录，解压后不知道双击哪个文件。
- **为什么必须简化**：这是第 0 步。走不过去，后面所有优化都白搭。

**[已确认] 问题 2 🟡 软卡点 —— README 的"安装"段落面向开发者**
`python -m venv .venv` / `.venv/bin/pip install -r requirements.txt` 这套命令对零基础用户是劝退级的。而实际上 Windows 用户**根本不需要执行这些**（`start.bat` 全自动做了）。两套并存的说明制造了困惑：用户会以为自己必须先跑这些命令。

---

### 阶段 1 · 装 Python

**当前做法**：`start.bat` 检测不到 Python 时打印指引，让用户去 python.org 下载。

**[已确认] 问题 3 🔴 硬卡点 —— 装 Python 有两个高概率翻车点**
1. 安装第一屏的 `Add python.exe to PATH` **不勾**（默认就是不勾的），于是装完了脚本还是找不到；
2. 系统自带的 **Microsoft Store 应用执行别名**抢占 `python` 这个名字，导致 `where python` 命中假货（这正是 v1.0.1 修的那个 bug）。

即使报了错并给出指引，**要求一个零基础用户去"设置 → 应用 → 高级应用设置 → 应用执行别名"里关开关**，本身就是个高门槛动作。
- **为什么必须简化**：这是第二大流失点。Windows 10/11 自带 `winget`，完全可以一条命令装好并自动处理 PATH，不需要用户去官网找安装包。

---

### 阶段 2 · 装 Python 依赖

**当前做法**：`start.bat` 执行 `pip install --quiet ... -r requirements.txt`。

**[已确认] 问题 4 🟡 软卡点 —— 没有国内镜像**
`pip` 默认走 `pypi.org`，国内直连经常几十 KB/s 甚至超时。安装 fastapi + uvicorn + httpx 可能耗时数分钟到失败。

**[已确认] 问题 5 🟡 软卡点 —— 静默安装 + 无进度**
`--quiet` 让整个过程**没有任何输出**。用户双击后看到的是一个黑窗口停在那里好几分钟，第一反应是"死机了"，然后关窗口 —— 于是半装的虚拟环境被留下，下次运行行为诡异。
- **为什么必须简化**：静默 + 无进度 = 用户在系统正常工作时报错退出。这是最典型的"冤枉流失"。

---

### 阶段 3 · 准备 llama.cpp（推理引擎）

**当前做法**：README 写「④ 配置 `llama-server.exe` 路径与端口」；UI 里是一个纯文本输入框。

**[已确认] 问题 6 🔴 硬卡点 —— 完全没告诉用户 llama-server.exe 从哪来**
我在全仓库检索 `llama.cpp/releases`、`llama-server.exe 下载` —— **零命中**。
用户需要自己知道：去 `github.com/ggml-org/llama.cpp/releases` 下载 Windows 构建包，从里面**十几个文件**中挑出 `llama-server.exe`，还得选对后端（Vulkan？ROCm？CUDA？CPU？），并知道这些 `*.dll` 必须和 exe 放在一起，否则报缺 DLL。
- **为什么必须简化**：这是**最大的单一卡点**。一个零基础用户不可能自行完成，而它又是整个工具的硬前提。

**[已确认] 问题 7 🟡 软卡点 —— 路径靠手输，且没有校验**
UI 里是 `<input type="text" placeholder="C:/llama/llama-server.exe">`。手打路径极易出错（斜杠方向、空格、中文目录）。而且**打错了不会立刻报错**，要等点了「开始测试」才失败。

---

### 阶段 4 · 准备 .gguf 模型

**[已确认] 问题 8 🔴 硬卡点 —— 没告诉用户模型从哪来**
扫描页只有一个 `路径` 输入框。用户需要自己知道：
- 什么是 GGUF；
- 去 Hugging Face / ModelScope 搜索 `GGUF` 版本；
- 一个仓库里往往有十几个量化版本（Q4_K_M / Q8_0 / IQ4_XS…）该下哪个；
- 大模型动辄 5–40 GB，下载慢、可能中断。

**[已确认] 问题 9 🟡 软卡点 —— 扫描页有空态但没有引导**
`app.js` 里没有任何"没有找到模型"的引导文案（检索"无匹配/未找到/空"零命中）。用户扫描一个空目录后，看到一片空白，不知道下一步该干什么。

---

### 阶段 5 · 填参数（当前最容易打击信心的一屏）

UI 第 ④ 页有 **20 个**可交互项。逐个看：

**[已确认] 问题 10 🟡 软卡点 —— 术语直接暴露，无解释**
| 字段 | 用户看到 | 真实含义 |
|---|---|---|
| `-ngl` | 一个光秃秃的缩写 | GPU 卸载层数 |
| 后端 `vulkan/cuda/rocm/metal/cpu` | 五个选项 | 图形 API，选错直接跑不起来 |
| `运行器模式 auto/real/mock` | mock（合成数据） | **内部测试开关，不该给用户看** |
| `连续失败跳过阈值` | 数字 | 内部状态机参数 |
| `单点超时(s)` | 1800 | 内部保护参数 |
| `预热次数` / `正式重复` | 1 / 3 | benchmark 统计方法 |

**[已确认] 问题 11 🔴 隐性风险 —— `mock` 模式让用户拿到假的性能数据**
`mock（合成数据）` 就这么摆在选项里，且 `auto` 在 llama-server 路径为空时会**自动降级到 mock**。一个零基础用户完全可能：没配 llama-server 路径 → `auto` 静默降级 → 跑完拿到一份漂亮的报告 → **以为那就是自己机器的性能**。
报告里虽然有 mock 标记，但用户是冲着"测我的机器"来的，这个误解代价很大。

**[已确认] 问题 12 🟡 软卡点 —— 没有任何耗时预估**
界面上只有「合计 N 点」。但实际耗时 ≈ 模型数 × 7 个 ctx 档位 ×（每次重启 llama-server 的加载时间 + 该档位点数 × 重复次数 × 单点耗时）。
跑一个 30B 模型的默认 49 组 × 3 次重复，**轻易就是几小时**。
用户点下「开始测试」时对时间毫无概念，中途会以为卡死了。

**[已确认] 问题 13 🟡 软卡点 —— 输出目录是相对路径**
`./reports` —— 用户跑完后不知道文件到底落在哪台盘的哪个文件夹。

---

### 阶段 6 · 跑测试

**[已确认] 问题 14 🟡 软卡点 —— 进度页没有时间信息**
进度页有 `模型 x/y`、`百分比`、`点数`、`当前 ctx/input`，但**没有已用时长、没有预计剩余时间**。

---

### 阶段 7 · 硬件前提（BIOS）

**[已确认] 问题 15 🟡 软卡点 —— BIOS 显存划分提示太晚**
"大 ctx 会 OOM，需先在 BIOS 划分 UMA 显存"只出现在 README 末尾和 Release 说明里。而 UI 里选 `64K/128K/256K` 档位时**没有任何提示**。
用户是看到报告里一排红色 `OOM_GPU` 才知道的 —— 那时已经白等了几小时，而且"进 BIOS 改显存划分"对小白是个大动作。

---

### 阶段 8 · 看报告

**当前做法**：报告是设计精良的单文件 HTML，有可折叠参数说明、曲线、悬停数值、10 列表格。

**[已确认] 问题 16 🟢 → 🟡 缺的只有"结论层"**
报告完整地**展示了数据**，但没有告诉用户**结论**：什么算好？我这台机器的表现是否正常？哪个档位是该模型的"甜点"？用户看完只有一堆数字。

---

## 三、改造方案（按执行顺序，P0 → P2）

> 排序原则：**先解决"能不能跑起来"，再解决"跑起来顺不顺手"，最后解决"看得懂"**。

### 第 1 批 · 让它能跑起来（解决 4 个硬卡点）

| # | 改造 | 针对问题 | 具体做法 |
|---|---|---|---|
| **P0-1** | **Release 附「开箱即用 ZIP」** | 问题 1、2 | 打一个 `gguf-benchmark-v1.0.1-win.zip`，解压后目录里只有一个 `start.bat`（及完整代码）。README 顶部改成两句话：「① 装 Python ② 双击 start.bat」 |
| **P0-2** | **`start.bat` 内置 `winget` 一键装 Python** | 问题 3 | 检测不到 Python 时，不只看指引，而是提示`[按 Y 自动安装]` → 执行 `winget install -e --id Python.Python.3.12 --scope user`，装完自动重查。**顺带解决**：winget 安装的 Python 不会产生商店别名冲突 |
| **P0-3** | **UI 内一键获取 llama.cpp** | 问题 6 | 后端新增 `POST /api/llama/download`：从 `ggml-org/llama.cpp` 的 latest release 拉 Windows Vulkan 构建 zip，解压到 `./llama.cpp/`，自动回填 `llama-server.exe` 全路径。UI 上是一个大按钮「一键获取 llama.cpp（约 200MB）」，带下载进度条 |
| **P0-4** | **模型获取指引 + 目录就绪校验** | 问题 8、9 | 扫描页空态显示：「没有 .gguf 模型？→ ① 去 ModelScope/Hugging Face 搜 `模型名 GGUF` ② 下载 `Q4_K_M` 或 `Q8_0` 版本 ③ 放进一个文件夹，把路径填在下面」，并给出 2 个可直接点的搜索链接。扫描前先校验该目录下确实有 ≥1 个可读 .gguf |

### 第 2 批 · 让它别在正常工作时被误解（解决软卡点）

| # | 改造 | 针对问题 | 具体做法 |
|---|---|---|---|
| **P0-5** | **pip 国内镜像 + 显示进度** | 问题 4、5 | `start.bat` 中 pip 加 `-i https://pypi.tuna.tsinghua.edu.cn/simple`（可用环境变量覆盖）；去掉 `--quiet`，改为打印「正在下载依赖…这一步只做一次」 |
| **P0-6** | **原生文件夹选择按钮** | 问题 7、13 | 后端新增 `POST /api/dialog/pick-dir` / `pick-file`，用 PowerShell 的 `FolderBrowserDialog`（Windows）/ `tkinter` 子进程（跨平台）弹系统对话框。扫描目录与 llama-server 路径都改成「选」而不是「打」。**顺带**：选完立刻校验（文件存在 + `llama-server --version` 能执行） |
| **P0-7** | **按本机预填 + 「高级设置」折叠** | 问题 7、10 | 后端新增 `GET /api/hardware/recommend`：检测到 AMD iGPU → `backend=vulkan`、`n_gpu_layers=99`、`threads=物理核数`。把 `-ngl`/后端/线程数/预热次数/正式重复/Decode 长度/失败阈值/单点超时 **全部收进「高级设置（一般不用改）」折叠区**，默认只露 4 项：模型目录、llama-server 路径、测试规模、开始按钮 |
| **P0-8** | **移除 mock 模式（对普通用户）** | 问题 11 | `runner_mode` 从 UI 移除，默认 `auto`。`auto` 降级到 mock 时：**进度页与报告顶部都显示醒目的橙色横幅**「⚠️ 本次为模拟数据，未调用真实推理」。mock 入口只保留在 URL 参数 / 高级区并二次确认 |
| **P0-9** | **耗时预估 + 运行中 ETA** | 问题 12、14 | 开始前：按「模型数 × 档位数 × 重复次数 × 经验单点耗时」给区间估算，显示「预计 40 分钟 ~ 1.5 小时」。开跑后：用**第一个完成的 ctx 档位**的真实耗时动态修正剩余时间（这是准的，因为耗时主要来自输入长度） |
| **P0-10** | **「先跑 1 档试跑」按钮** | 问题 12 | 在「开始测试」旁放一个次级按钮「先试跑 1 个档位（约 1 分钟）」：只跑 ctx=4K / input=0.25K。让用户用极小代价确认「llama-server 路径对不对、模型能不能加载、报告长什么样」，再决定要不要投入几小时 |
| **P0-11** | **输出目录绝对化 + 一键打开** | 问题 13 | 配置项显示解析后的绝对路径；完成页给「打开报告所在文件夹」按钮 |

### 第 3 批 · 让它把话说清楚

| # | 改造 | 针对问题 | 具体做法 |
|---|---|---|---|
| **P1-1** | **BIOS 显存提示前置** | 问题 15 | 在测试维度区：用户勾选 ≥64K 的 ctx 档位时，就地弹出提示「本机若未在 BIOS 划分 UMA 显存，64K 以上档位会 OOM，建议先只跑 ≤32K，或确认显存已划分」。不需要用户去 README 里翻 |
| **P1-2** | **错误码 → 人话 + 动作** | — | 每个 `E_*` / `fail_reason` 都配两行：「这是什么意思」「你该怎么做」。例：`E_MODEL_FAIL` → 「模型没能加载。常见原因：文件不完整或不是有效的 .gguf。建议重新下载该模型文件。」 |
| **P1-3** | **首次打开显示「三步上手」向导** | 问题 1、3、6、8 | 第一次访问 UI 时，用一张卡片把三件事列清：① 装 Python（自动）② 获取 llama.cpp（一键）③ 准备模型（指引），每步一个按钮/链接，完成一项打勾 |
| **P1-4** | **报告加「结论层」** | 问题 16 | 报告顶部加「这份报告怎么看」三行：Prefill 越高越好 / Decode 曲线越平说明长上下文衰减越小 / 出现红色 OOM 说明显存不足需要去 BIOS 划分。再加一句自动生成的结论，如「本机在该模型上的最佳工作区间是 ctx ≤ 32K」 |

### 第 4 批 · 加分项

| # | 改造 | 说明 |
|---|---|---|
| **P2-1** | **GitHub Pages 在线演示** | 让用户在装任何东西之前，先点开看到报告长什么样（现有 `docs/demo/overview.html` 直接托管即可） |
| **P2-2** | **许可证** | 目前无 License，法律上默认「保留所有权利」，会阻碍他人使用 |
| **P2-3** | **一键导出报告到桌面** | 报告已是单文件，加个「保存到桌面」按钮 |
| **P2-4** | **`start.bat` 首次运行打印「预计 3 步、约 2 分钟」** | 给用户一个预期，减少中途放弃 |

## 四、改造后的目标流程（对照）

| 现在（8 步，4 个硬卡点） | 改造后（4 步，0 个硬卡点） |
|---|---|
| 1. 想办法下载源码 | **1. 下载 Release 的 ZIP，解压** |
| 2. 去官网装 Python（易翻车） | **2. 双击 start.bat（没装 Python 会问你一句就自动装）** |

| 5. 自己找 .gguf 模型 | |
| 6. 手打路径 + 理解 20 个参数 | |
| 7. 盲等数小时 | |
| 8. 报告 OOM 才知道要改 BIOS | |

## 五、建议的落地顺序（若要我实施）

1. **P0-1 ~ P0-4**（打 ZIP、winget 装 Python、一键获取 llama.cpp、模型指引）—— 这四项做掉，硬卡点归零，是最有杠杆的一批
2. **P0-5 ~ P0-8**（镜像+进度、原生选择器、预填+高级折叠、移除 mock）—— 把"冤枉流失"和"数据误解"消掉
3. **P0-9 ~ P0-11**（耗时预估、试跑、输出路径）—— 降低决策焦虑
4. **P1 全部**（BIOS 提示、人话错误、上手向导、报告结论层）
5. **P2** 视情况

> 说明：本方案只做审计与设计，**尚未改任何代码**。确认后我按批次实施，每批都补对应的回归断言。
